1. 專案總覽

Deep Research Skill 是一個專為 Claude Code 設計的「深度研究技能」（Skill）。 它本身不是執行階段（runtime）的代理框架，而是一組由 Markdown 指引文件、 JSON Schema 契約、Python CLI 工具 與 HTML / Markdown 樣板 所組成的「研究工作流腳手架」。Claude Code 模型本身擔任協調者（orchestrator），透過 這些檔案規範研究流程，並在過程中將每一筆 source、evidence、claim 持久化到磁碟， 以便支援上下文壓縮（context compaction）、長報告續寫（continuation agent）以及 引用驗證。

1.1 設計哲學

  • Claude 是執行者，腳本是契約：research_engine.py 在首部 即標明「STATE SCAFFOLD (not a runtime orchestrator)」。Python 端只提供 指令範本與狀態 I/O，真正驅動研究的是模型自身。
  • 內容尋址（content-addressable）的證據基底：source、evidence、claim 三者皆以 SHA-256 截斷哈希作為穩定主鍵，使「重排引用編號」「續寫」「壓縮上下文」 都不會破壞引用關聯。
  • Append-only JSONL：所有研究痕跡（資料、證據、論點）採只追加日誌， 天然支援多 agent 並行寫入與審計回溯。
  • 引用幻覺零容忍：verify_citations.py 內建 CiteGuard 2025 模式比對與 DOI / URL 雙重驗證；verify_claim_support.py 進一步驗證每一句 論點是否確實有證據支撐。

2.2 模組相依關係

模組之間刻意保持低耦合，主要依賴是「共享磁碟資料夾」而非 Python import：

  • citation_manager.py 寫入 sources.jsonl 與 run_manifest.json。
  • evidence_store.py 透過 source_id 引用 source， 寫入 evidence.jsonl。
  • extract_claims.py 解析報告 markdown，寫入 claims.jsonl。
  • verify_claim_support.py 同時讀三份 JSONL，更新 claim 的 support_status。
  • validate_report.py 與 verify_citations.py 只讀 report.md，獨立檢查結構與引用合法性。

4. 資料層：JSONL 證據基底

每次研究會在 ~/Documents/[Topic]_Research_[YYYYMMDD]/ 建立一個 研究資料夾，內含：

  • run_manifest.json：研究設定與假設清單。
  • sources.jsonl：來源註冊表（append-only）。
  • evidence.jsonl：證據條目（append-only）。
  • claims.jsonl：原子化論點與支撐狀態。
  • report.md：主報告（markdown）。

4.1 三個內容尋址 ID

source_id   = sha256(canonical_locator)[:16]
evidence_id = sha256(source_id + normalize(quote) + locator)[:16]
claim_id    = sha256(section_id + normalize(text))[:16]

這個設計帶來幾個關鍵性質：

  • 冪等註冊：相同 URL 多次註冊只會產生同一個 source_id， cmd_register_source 在 append 前會線性掃描去重。
  • 展示編號與身分分離：[1] [2] [3] 是 render-time 指派，由 assign-display-numbers 動態產生，因此編輯／續寫不會 造成引用斷鏈。
  • 跨 agent 共享狀態：續寫代理只要拿到資料夾路徑即可重建完整 引用上下文。

4.2 Canonical Locator 規則

citation_manager.canonicalize_locator() 採以下優先序：

  1. 若 URL 含 doi.org/10.x/... 或 doi: → 標準化為 doi:10.xxxx/yyy（去尾部句點）。
  2. 若 URL 含 arxiv.org/abs/ 或 arxiv: → 標準化為 arxiv:2305.14251。
  3. 否則回退到「URL 標準化」：lower-case scheme/host、去 fragment、去 utm_*/fbclid/gclid 等追蹤參數， 並對保留下的 query 排序。

這個三段式策略讓「同一篇論文的 PDF/DOI/arXiv 鏡像」高機率被識別為同一來源， 顯著減少重複引用。

5. 核心腳本逐一拆解

5.1 citation_manager.py

管理「來源身分」與「研究 run」兩件事，提供四個子指令：

指令功能輸出
init-run建立 manifest 與三個空 JSONLrun_manifest.json
register-source標準化 URL → 計算 source_id → appendJSON：{status, source_id}
assign-display-numbers依註冊順序給予顯示編號JSON map：{source_id: N}
export-bibliography輸出 markdown 或 JSON 參考書目STDOUT

5.2 evidence_store.py

追加式證據庫。每筆證據必須提供 source_id 與 quote，並可選 locator（頁碼/章節/錨點）、 retrieval_query、evidence_type。 evidence_type 限定為 direct_quoteparaphrase data_pointfigure_reference methodology，預設值為 direct_quote。

5.3 source_evaluator.py

純 Python、純啟發式的信譽評分器，輸出 CredibilityScore 物件， 包含四個分項：

  • domain_authority (35%)：兩級白名單。HIGH 域名（arxiv、nature、 nih.gov 等）→ 90；MODERATE（techcrunch、wikipedia 等）→ 70； LOW 指標（blogspot、wordpress 等）→ 40；未知 → 55。
  • recency (20%)：<90d → 100；<1y → 85；<2y → 70； <5y → 50；其餘 30。
  • expertise (25%)：學術/政府/官方文件加分，作者頭銜 （Dr./PhD/Professor）+15。
  • bias (20%)：標題含「!、shocking、secret」扣分； 含「however、although」加分。

最終 overall 對應到 high_trust / moderate_trust / low_trust / verify 四級。

5.4 verify_citations.py（CiteGuard 2025）

對 ## Bibliography 區段做四步檢查：

  1. 幻覺模式偵測：用 regex 抓「A Study of …」「Recent Advances in …」 等典型 LLM 編造模式；偵測未來年份、太短的通用標題、placeholder 文字、 過去年份配上現代術語（如 1995 + LLM）。
  2. DOI 解析：透過 doi.org content-negotiation 取得 CSL-JSON metadata，比對標題（Jaccard 相似度）與年份。
  3. URL HEAD 請求：DOI 失敗時退而求其次，檢查連結可達性。
  4. 無 DOI 也無 URL：標記為 suspicious。

腳本支援 --strict 旗標：任何 suspicious 即非零退出，可作為 CI gate。

5.5 extract_claims.py

讀取 markdown 報告，依預先定義的章節 regex 切段，再以「(?<=[.!?])\s+(?=[A-Z])」 做樸素句子切割。每句 ≥30 字符且非標題、表格列即視為候選論點，並做啟發式分類：

  • recommendation：含 should/recommend/suggest/advise/consider。
  • speculation：含 might/could potentially/it is possible/may eventually。
  • synthesis：在 synthesis/conclusion/limitations 章節且含 「overall、taken together、the evidence suggests」。
  • factual：預設。

分類意義在於 verify_claim_support.py 對不同類型有不同嚴格度： 只有 factual 類論點會 hard-fail。

5.6 verify_claim_support.py

完全確定性、無 LLM 呼叫的論點驗證器。對每一個 claim：

  1. 從 cited_source_ids + evidence_ids 收集所有候選引文。
  2. 對每段 quote 計算四個重疊率：
token_overlap = |claim_tokens ∩ ev_tokens| / |claim_tokens|       # 4+ 字小寫詞
number_match  = |claim_numbers ∩ ev_numbers| / |claim_numbers|
year_match    = |claim_years ∩ ev_years| / |claim_years|
entity_match  = |claim_entities ∩ ev_entities| / |claim_entities|  # 樸素 NER

score = 0.4*token + 0.25*number + 0.15*year + 0.2*entity

取所有候選 quote 的最高分作為該 claim 的支撐分數，並依門檻歸類： ≥0.6 supported、≥0.35 partial、其他 needs_review。 無證據時的分支有兩種：(a) 完全沒有任何 cited_source_ids、 evidence_ids 與 quote → speculation 類視為 supported，其餘為 unsupported；(b) 有 cited 或 evidence 連結但實際抓不到任何 quote → 一律 needs_review。--strict 模式下 「factual + unsupported」即非零退出。

5.7 validate_report.py（9 項結構檢查）

  1. Executive Summary 存在且字數 ~200-400。
  2. 必備章節（Introduction、Main Analysis、Synthesis、Limitations、 Recommendations、Bibliography、Methodology）齊全。
  3. 引用數 ≥10 且 [N] 編號連續。
  4. Bibliography 涵蓋所有 [N]、無 placeholder（如 [8-75]、 Additional citations…）。
  5. 無 TBD/TODO/FIXME 等標記。
  6. 無內容截斷模式（Content continues、Due to length、[Sections X-Y]）。
  7. 字數合理。
  8. 來源數 ≥10。
  9. 內部連結（./...）有效。

區分 errors 與 warnings：errors 任一非零即不通過，warnings 不阻擋但會列出。

5.8 md_to_html.py + verify_html.py

自寫 markdown→HTML 轉換器（不依賴 markdown 套件，純 regex 與行掃描）， 將每個 ## 包成 <div class="section">， 保留 [N] 引用便於後續 tooltip 注入。verify_html.py 比對 MD/HTML 章節數、檢查未替換的 {{...}} placeholder、確認沒有 emoji （此 skill 嚴格禁止輸出 emoji）。

5.9 research_engine.py

本檔不是真正的協調者，而是「階段指令範本庫 + 狀態序列化」。對於每個 ResearchPhase 提供一段對 Claude 的提示（instructions）， 並提供 ResearchState dataclass 的 save/load。 這也是整個 skill「Claude 是執行者，腳本是契約」哲學最直接的體現。

7. 優點分析

7.1 引用與證據的工程化處理

  • 三層內容尋址讓引用脫離「順序敏感的 [1][2][3]」，這在 LLM 編輯／壓縮上下文時尤為關鍵。多數同類框架仍把 [N] 當主鍵，續寫時容易斷鏈。
  • 純啟發式的 claim-support 驗證無需呼叫 LLM，CI 友善，成本可控； 針對 factual 類型才 hard-fail，務實。
  • CiteGuard 模式庫把 LLM 常見的「假論文標題」抓住（A Study of …、 future year、anachronistic AI 引用），第一線就過濾大量幻覺。

7.2 工程實作品質

  • Python 3.9+ 標準函式庫，requirements.txt 內無 pip 相依，部署門檻極低。
  • CLI 都採 argparse + 子指令模式，輸出 JSON 至 stdout，方便其他 agent 以 Bash 呼叫並 JSON.parse。
  • JSONL append-only 設計天然支援並行寫入與審計回溯。
  • JSON Schema (draft-2020-12) 對每個資料形狀都做嚴格定義，並用 additionalProperties: false 防止欄位漂移。
  • research_engine.py 的 save 含 retry + exponential backoff， 對 IO 競爭友善。

7.3 工作流設計

  • Step 0「先抓今天日期」避免模型用訓練資料預設年份做時間查詢。 這是非常聰明的小設計。
  • FFS（First Finish Search）讓並行檢索達門檻即進入下一階段， 其餘背景搜尋的結果仍可餵入 SYNTHESIZE。
  • OUTLINE REFINEMENT (4.5) 與 critique loop-back是 WebWeaver 風格 的動態大綱演化，避免「鎖定錯誤框架」。
  • 多人格紅隊（Skeptical Practitioner / Adversarial Reviewer / Implementation Engineer）讓 Deep/Ultra 模式具備可操作的批判視角。

8. 缺點、風險與技術債

8.1 設計層面

R1 — 純啟發式驗證的天花板。 verify_claim_support.py 用 token/number/year/entity 四個 Jaccard 式重疊率組合而成，對「同義改寫」「跨語言」「需邏輯推論的支撐關係」幾乎無能為力。 一個被改寫得很好的真實引用可能被打到 partial 甚至 needs_review；反之，token 大量 重疊但語義相反的 quote 可能被誤判為 supported。
R2 — 信譽白名單的可維護性。 source_evaluator.py 把幾十個域名硬編碼到集合中，新領域（如各國政府網站、 區域性學術出版社）需要持續維護。沒有外部資料源（如 OpenAlex、CrossRef、 Tranco/MOZ DA）作備援。
R3 — Bibliography parser 過度依賴特定字串格式。 verify_citations.extract_bibliography() 假設條目格式為 [N] Author (Year). "Title". Venue. URL，模板實際輸出格式 [N] Author. (Year). [Title](URL) 與此不符（title_match 依賴雙引號），易導致 title/year 抽取失敗。
R4 — md_to_html.py 為自寫轉換器。 沒用成熟函式庫（如 markdown-it-py），對巢狀清單、code fence、 HTML escape、巢狀 emphasis 的處理脆弱。例如 _convert_lists() 用 '
    ' in '\n'.join(result[-10:]) 的字串掃描判斷有序/無序， 在複雜輸入下可能誤判。

8.2 工程層面

  • 耦合測試：超過一半腳本沒有單元測試覆蓋；source_evaluator.py 甚至連基本 fixture 都沒有。
  • 效能：cmd_register_source 每次都用 O(n) 線性掃描判重， 當 sources 上千時會變慢；可考慮一次性建立 in-memory set 或外加 index 檔。
  • 路徑硬編碼：research_engine.py 預設輸出到 ~/.claude/research_output/，但 SKILL.md 又寫 ~/Documents/[Topic]_Research_[YYYYMMDD]/，兩個慣例並存易混淆。
  • 沒有並發鎖：JSONL append 在多 agent 同時寫入時可能交錯 （單行 write 在多數 OS 上確實 atomic，但缺少明示文檔；若改成多行 record 將易壞）。
  • 無 lock 檔避免重複 init-run：呼叫者可能無意間再執行 init-run，雖然有「if not os.path.exists」保護 artifact 檔，但會覆寫 run_manifest.json。

8.3 流程層面

  • 對 search-cli 的耦合：methodology 把 search-cli 列為「primary」 並要求模型優先呼叫；但這只是 brew 安裝的第三方 CLI，企業環境難以部署。 WebSearch fallback 的職責切換策略沒明文規範。
  • QPS / cost 控制缺失：「並行 5-10 次搜尋 + 2-3 個 sub-agent」 的策略沒納入 token / 金錢預算，UltraDeep 模式可能燒得很兇。
  • 資訊來源缺乏 PDF/長文擷取的標準化路徑：仰賴 search -m extract 的黑箱。
  • 無多語言支援：所有 prompt、模板、validator 預設英文； 對非英語題材（如本次的繁中報告）幾乎沒有現成 hook。

9. 深度章節：Search → Citation 完整生命週期

本節是本份分析的重心。我們把整個從「使用者下達研究指令」到「最終 HTML/PDF 包含可信引用」的過程拆解成 12 個明確階段，並對應到具體腳本與資料檔。

  1. 研究啟動：建立 Run 容器

    模型決定模式（quick/standard/deep/ultradeep）後，在 ~/Documents/[Topic]_Research_[YYYYMMDD]/ 建立資料夾並執行： 

    python scripts/citation_manager.py init-run \
  --out-dir [folder] --query "[原始問題]" --mode [mode]

    產出 run_manifest.json（含版本 3.0.0、started_at、 provider_config、artifact_paths）以及空的 sources.jsonl、 evidence.jsonl、claims.jsonl。從此刻起，所有狀態 都「離開模型上下文，落入磁碟」。

  2. Step 0：取得當前日期

    模型在「單一訊息中」發出多個 Bash 工具呼叫，並可選配 幾個 Task sub-agent 處理 PDF / repo 深挖。每個 sub-agent 的輸出強制為 結構化 JSON：

    報告寫完後執行： 

    python scripts/extract_claims.py extract --report [path]/report.md --dir [folder]
python scripts/verify_claim_support.py verify --dir [folder] --strict

    extract_claims 會把每節切成原子論點並依 regex 啟發式分類為 factual / synthesis / recommendation / speculation。verify_claim_support 再用 token+number+year+entity 四維 Jaccard 加權打分；--strict 模式下若有任一 factual claim 為 unsupported 即非零退出，迫使模型回去補證據。

  12. 結構與引用最終驗證

    最後一道閘門： 

    python scripts/validate_report.py --report [path]/report.md
python scripts/verify_citations.py --report [path]/report.md
python scripts/citation_manager.py export-bibliography --dir [folder] --style markdown
python scripts/md_to_html.py [path]/report.md
python scripts/verify_html.py --html [path]/report.html --md [path]/report.md

    validate_report 跑 9 項結構檢查；verify_citations 做 DOI/URL/CiteGuard 比對；md_to_html + verify_html 完成排版與一致性檢核。 三個 validator 中任一失敗 → 進入「validate → fix → retry」迴圈， 最多 3 輪。

關鍵不變量： 在整個生命週期中，source_id、evidence_id、 claim_id 一旦寫入即不變；[N] 顯示編號永遠在 render time 重新計算。這保證了「重排引用順序」「續寫」「更換引用樣式」三種操作不會破壞 引用網路的完整性。

# 五、verify_claim_support 演算法（請完全照抄）
================================================================
對每一個 claim：
  收集 quotes = [evidence.quote for ev_id in claim.evidence_ids 若 ev_id 在 evidence.jsonl 中]
              + [所有 source_id ∈ claim.cited_source_ids 之全部 evidence.quote]
  若 quotes 為空且 cited_source_ids 為空且 evidence_ids 為空：
     若 claim_type=='speculation' → support_status='supported'，否則 'unsupported'
  否則若 quotes 為空（即有 cited/evidence 連結但抓不到任何 quote）→ 'needs_review'
  否則對每段 quote 計算：
     claim_tokens   = re.findall(r'\b[a-z]{4,}\b', text.lower())
     claim_numbers  = re.findall(r'\b\d+(?:\.\d+)?(?:%|x|X)?\b', text)
     claim_years    = re.findall(r'\b(19|20)\d{2}\b', text)
     claim_entities = re.findall(r'\b[A-Z][a-z]+(?:\s+[A-Z][a-z]+)*\b', text)
                      減去停用詞 {The,This,That,These,However,Furthermore,
                      Moreover,Additionally,Therefore,Nevertheless}
     對 evidence quote 同樣抽取四個集合。
     token_overlap = |claim ∩ ev|/|claim|（claim 集合空則為 0）
     number_match  = |claim ∩ ev|/|claim|（claim 空則為 1）
     year_match    = 同上
     entity_match  = 同上
     score = 0.4*token + 0.25*number + 0.15*year + 0.2*entity
  取所有 quote 中最高 score：
     ≥0.6 → 'supported'； ≥0.35 → 'partial'； 否則 'needs_review'。

11. 結論與後續建議

Deep Research Skill 是少數把「LLM 研究流程」當成嚴肅軟體工程問題處理的 skill。它最具差異化的貢獻是「把引用變成內容尋址資料庫」， 讓引用的完整性脫離模型上下文的脆弱性。verify_claim_support.py 雖然演算法樸素，但「便宜、可重複、CI 友善」三個性質讓它非常實用。 CiteGuard 模式則是對 LLM 引用幻覺的有效一線防線。

若要進一步強化，建議的優先項目：

  1. 把 bibliography 解析從 regex 改為結構化 JSON 渲染， 讓 citation_manager export-bibliography 與 verify_citations 共用同一條解析規則，避免格式漂移。
  2. 增加 LLM-judge 補位：對 partial / needs_review 的 claim 才呼叫 LLM 做二次裁決，兼顧成本與召回率。
  3. 整合 OpenAlex / CrossRef：取代硬編碼信譽白名單，並用 OpenAlex 的 concept 欄位做主題相關性。
  4. 補齊測試：至少為 validate_report、 verify_citations、md_to_html、 source_evaluator 加上回歸 fixtures。
  5. 多語言支援：把 STOP_ENTITIES、章節 regex、 模板抽成 i18n 資源，讓繁中/日文/韓文題材也能跑。
  6. 明示 IO 鎖：在 append_jsonl 加 fcntl.flock()（POSIX）或 portalocker，避免多 agent 並發 寫入交錯。
